# Manual verification register

Scenarios listed here have no automated test whose name contains their title. Each entry
documents how it was verified and why automating it is not reasonable — see the
`journey-verification` capability's "Scenario-to-test traceability" requirement and
`scripts/check-traceability.mjs`. Keep this register short: prefer adding or renaming a test over
adding an entry here.

| Capability | Scenario | How verified | Why not automated |
| --- | --- | --- | --- |
| local-deployment | Fresh start with default configuration | Ran `docker compose down -v && docker compose up --build` in a fresh clone with no `.env` file; confirmed `http://localhost:8080` served the app and `GET /api/health` reported healthy through it. | Requires building and starting the full three-container stack (Postgres, API, nginx-fronted web) from a clean Docker state; the browser suite's `docker-compose.e2e.yml` deliberately runs a different configuration (`DEMO_DATA=false`, a fixed e2e admin, throttling disabled), so it doesn't exercise this exact "fresh clone, defaults only" path, and duplicating a full image rebuild as an automated check would make every CI run several minutes slower for a scenario that only changes when the Dockerfiles or compose defaults change. |
| local-deployment | Data survives a restart | With the stack from the previous check still running, ran `docker compose down` (no `-v`) then `docker compose up -d` again, and confirmed the same 15 demo user rows were present afterward (no re-seed, no data loss). | Same reason as "Fresh start with default configuration": needs a real container stop/start cycle against a named Docker volume, which is Docker Compose lifecycle behavior, not application behavior a unit/API/browser test can simulate. |
| local-deployment | Empty database | Ran `prisma migrate deploy` against a freshly created Postgres database (no prior schema) as part of the same `docker compose up --build` run above, and confirmed the API reported healthy afterward, which only happens once every migration (including enabling `btree_gist` for the exclusion constraints) has applied cleanly. | The API e2e suite's own test database is migrated once, ahead of the whole run, and reused across all 46 spec files — asserting "empty database" behavior would mean either tearing down and re-migrating a shared database mid-suite (making every other e2e test order-dependent) or standing up a second, disposable Postgres purely for this one assertion, both of which cost much more than the scenario is worth; the real, unattended proof is the same `docker compose up --build` run above. |
| local-deployment | Already migrated database | Ran `prisma migrate deploy` a second time against the already-migrated database from the check above; Prisma reported "No pending migrations to apply" and the schema was left untouched. | Same infrastructure reason as "Empty database" — this is a Prisma CLI/migration-history behavior at the database level, not something the running application's own test suite exercises. |
| local-deployment | Offline operation after build | Verified by code review: `apps/api`'s `package.json` dependencies and every service class were audited for outbound HTTP/SDK calls (see `CLAUDE.md`'s "Mandatory technical constraints" — no external SaaS/BaaS/runtime API is used anywhere in the running application), and `docker-compose.yml` defines only the `postgres`, `api`, and `web` containers with no external network dependency declared. | Actually cutting outbound network access to the Docker daemon/containers is a host-level network-namespace change outside what a Compose-based CI job or this test suite can safely or portably do; the guarantee this scenario is really checking — "nothing in the runtime path calls out to the internet" — is structural (no such client exists in the dependency graph) rather than something that needs to be observed by disconnecting a cable. |
| local-deployment | Ready to explore | Ran `docker compose down -v && docker compose up --build` in a fresh clone with no `.env` file, then signed in with all three documented credential sets (administrator, `doctor@demo.telehealth.local`, `patient@demo.telehealth.local`) via the running stack at `http://localhost:8080` and confirmed each succeeded and returned a populated user. | Same reason as "Fresh start with default configuration": this is the demo-data-populated variant of the same full-stack, fresh-container scenario, and the browser suite's `docker-compose.e2e.yml` deliberately sets `DEMO_DATA=false` for deterministic test data, so no automated suite exercises "the real default configuration, populated, from a truly fresh clone" without a second full stack build dedicated to this one scenario. |
| journey-verification | Journey failure fails CI | Temporarily changed one assertion in `e2e/tests/journey.spec.ts` to an unsatisfiable expectation, ran `pnpm exec playwright test tests/journey.spec.ts` against a running e2e stack, confirmed the process exited non-zero (`1`) with the expected failing assertion reported, then reverted the change and confirmed the suite passed again. | The scenario describes a general property of how process exit codes propagate to CI ("a failing test step fails the CI run"), which is a property of the shell/CI runner, not of this repository's code — there's no application behavior to assert against without either permanently leaving a test broken (defeating its own purpose) or building a meta-test that triggers a real CI run and inspects its outcome via the GitHub Actions API, which is disproportionate machinery for a guarantee `run: pnpm test` already provides by construction (a non-zero exit fails the step). |
| product-website | Build contains no external references | `apps/web/scripts/check-no-external-urls.mjs`, run via `pnpm --filter web run check:assets` as its own step in `.github/workflows/ci.yml` on every push and pull request; a build with any disallowed external reference fails that CI step. | The check is already fully automated (it runs on every CI push), but it's a standalone build-output scanner over `dist/`, not a `describe`/`it`-style test the traceability scanner can see by name; wrapping it in a redundant Vitest shell around its own `main()` would add a test file without adding any coverage the CI step doesn't already provide. |
| technical-documentation | All sections reachable from navigation | Read `docs/.vitepress/config.ts`'s `nav`/`sidebar` entries against the required section list (Technical Overview, C4 L1–L3 + Deployment, one Detailed Architecture page per module, API Documentation) and clicked through each link in a local `pnpm docs:dev` preview. | VitePress navigation reachability is a rendered-site structural property; asserting it would mean either parsing the built HTML's nav DOM (brittle against VitePress's own markup/version) or driving a browser through the docs site, which is disproportionate for a documentation-only capability with no user-facing runtime behavior. |
| technical-documentation | Incomplete sections are labeled | Read every page under `docs/modules/` and `docs/architecture/`; each references only capabilities that are implemented (every OpenSpec change through `add-product-website` is archived), so there is currently no "planned" section left to label — re-checked as part of this change's task 5.1 sweep for stale "planned" copy. | This is a content-authoring convention ("say a section is planned if it is"), checked by reading the docs prose against the current set of archived changes, not a property a test can evaluate — there's no programmatic way to tell "this page accurately describes what's implemented" from "this page is lying." |
| technical-documentation | Diagrams render on build | `docs/scripts/validate-mermaid.mjs` parses every Mermaid code block in `docs/**/*.md` with the real `mermaid` library during `pnpm docs:build` (wired as VitePress's `prebuild`/`predev` hook) and throws — failing the build — on any syntax error; confirmed by running `pnpm docs:build` and observing the diagrams render as images in the output. | Same shape as the "Build contains no external references" entry: the check is fully automated and already runs on every docs build, but it's a build script, not a named `describe`/`it` test. |
| technical-documentation | Container diagram matches the runtime | Read `docs/architecture/c4-container.md`'s Mermaid source directly against `docker-compose.yml`: it shows the web application calling the API over REST/JSON and WebSocket, the API calling PostgreSQL, and no other system inside or outside the boundary. | A diagram's semantic content ("does this box-and-arrow drawing match reality") is a documentation-accuracy judgment made by reading the diagram source next to the actual compose file and API routes, not something a rendering or syntax check (which only proves the Mermaid is well-formed) can verify. |
| technical-documentation | Generation without a database | Ran `pnpm openapi:generate` with `DATABASE_URL` unset in the shell; it completed successfully and produced `packages/api-client/openapi.json` and `schema.d.ts`, because Prisma's adapter connects lazily (see `CLAUDE.md`'s Prisma 7 gotcha) and the OpenAPI document is built from Nest's route/DTO metadata, not a live query. | Exercising this in the API e2e suite would require unsetting `DATABASE_URL` for one spec file while every other file needs it set, which Jest's shared `setup-env.ts` doesn't support per-file without either a second Jest project/config just for this one assertion or monkey-patching `process.env` mid-suite (itself a source of test-order bugs) — disproportionate for a one-line CLI behavior already documented in `CLAUDE.md` and exercised by hand whenever the OpenAPI document changes. |
| technical-documentation | Stale generated artifacts | This is `.github/workflows/ci.yml`'s "Regenerate OpenAPI document and client, then check for drift" step (`pnpm openapi:generate` followed by `git diff --exit-code` on the generated files) and the equivalent "Regenerate the data model ER diagram" step — both run on every push and pull request. | A `git diff --exit-code` freshness check only means something inside a real git working tree with a prior commit to diff against; it can't be expressed as a `describe`/`it` assertion without shelling out to git from inside the test runner and asserting on a git-only precondition (a clean, committed baseline) that a unit test isn't set up to guarantee. |
| technical-documentation | Push to main | Read `.github/workflows/docs.yml`: its `on.push.branches: [main]` trigger builds the docs and deploys via `actions/deploy-pages`, matching this scenario exactly. | This describes GitHub Actions' own trigger behavior on a real push to the hosted repository's default branch — nothing reachable from a local test run (there is no "main branch" or GitHub Pages environment inside this workspace to push to and observe a deployment from). |
| technical-documentation | Served from a repository subpath | Read `docs/.vitepress/config.ts`'s `base: process.env.DOCS_BASE \|\| '/'` and `docs.yml`'s `env: DOCS_BASE: /${{ github.event.repository.name }}/` on the build step, confirming every link VitePress generates is base-relative rather than root-absolute. | Verifying "no broken links once actually served under a GitHub Pages subpath" needs a real GitHub Pages deployment (or an equivalent subpath-serving proxy) to click through, which doesn't exist in this local/CI environment; the base-path configuration itself is the property that's actually reviewable. |
| technical-documentation | Local preview | Ran `pnpm docs:dev` and confirmed the site served locally with live reload on editing a page. | "Serves locally with live reload" is VitePress dev-server behavior (inherited from Vite) being exercised as intended, not application logic; there's nothing project-specific here for a test to assert beyond "the dev server starts," which the CI build step already exercises indirectly by using the same VitePress toolchain. |
